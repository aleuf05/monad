# Architecture Note -- The Living Basin v0

A concise map of how the prototype is built and why, for anyone who wants
to modify it rather than just run it.

## Layout

```
tools/living-basin/           Python reference engine (local, not web-facing)
  engine/                       simulation engine (no rendering code in here)
    config.py                     documented field ranges + all tunable constants
    grid.py                       World: field storage, elevation, 8-neighbor flow
    weather.py                    scripted rain schedule (stateless, reusable)
    hydrology.py                  rainfall, infiltration, evaporation, flow redistribution
    vegetation.py                 biomass growth, root-density lag
    herbivores.py                 agents: weighted movement + grazing
    trails.py                     trail accumulation/decay
    erosion.py                    cohesion relaxation, threshold-gated erosion
    events.py                     append-only Event / EventLog, causal traversal
    features.py                   FeatureRegistry (WaterPool/HerbivoreTrail/GrazedPatch/ErosiveGully)
    lineage.py                    deterministic, template-based diagnostic-card text
    overrides.py                  authored-override recording
    simulation.py                 Simulation: the ordered tick pipeline
  scenario.py                  the one deterministic acceptance-demonstration seed/config
  run_demo.py                  CLI: runs scenario.py, writes data/ (local verification only)
  tests/                       unittest suite (pytest-compatible), Python engine only
  data/                        generated by run_demo.py -- not checked in, regenerate it

web/toys/living-basin/        the live public page (this IS the interface -- no staging copy)
  engine.js                     hand-ported mirror of engine/*.py, ticks live in-browser
  app.js                        drives the live Simulation; builds diagnostic cards from it
  index.html, style.css         page shell and styling
```

The Python engine has zero dependency on any rendering or file format; it
operates purely on in-memory Python objects, and `run_demo.py` is the only
place that serializes anything (for local verification and the sample
screenshot). The live page does not read that output at all --
`web/toys/living-basin/app.js` constructs a `Simulation` directly from
`engine.js` and ticks it client-side. There is deliberately no third,
"staging" copy of the viewer anywhere in the repo: an earlier version of
this prototype kept a `tools/living-basin/viewer/` copy that got synced to
`web/` after the fact, which is exactly the staging pattern this project's
own policy rejects (see `CLAUDE.md`'s "no staging environment" and "one
source of truth" policies) -- it was removed once that was pointed out.

## Tick pipeline (exact order, see `Simulation.tick`)

1. weather (rain-schedule lookup)
2. rainfall deposition
3. water infiltration + evaporation
4. flow-direction recompute + surface-water redistribution (runoff)
5. vegetation growth / stress
6. root-density update (lags biomass -- see below)
7. herbivore movement
8. grazing (inseparable from movement: an agent grazes the cell it moves onto)
9. trail accumulation
10. soil cohesion update
11. erosion
12. feature detection
13. provenance recording

This order is fixed and asserted by `tests/test_determinism.py` indirectly
(any accidental reordering changes the checksum). All randomness comes from
two `random.Random` instances seeded from the simulation seed: one for
herbivore movement (`Simulation.rng`), one for elevation roughness
(consumed once, inside `grid.generate_elevation`). No other randomness
exists anywhere in the pipeline.

## Modeling choices, made explicit (not claimed as physically accurate)

- **8-neighbor flow.** Both water flow and herbivore movement use the full
  8-neighbor set, not just the 4 orthogonal neighbors, so diagonal terrain
  features aren't artificially blocked.
- **Steepest-descent flow with a knickpoint exception.** `World.local_slope`
  is the drop to a cell's downhill 8-neighbor (0 for a local minimum).
  Erosion additionally checks `World.inflow_slope` -- the steepest drop
  *from* an uphill neighbor *into* the cell -- because a real hollow fed by
  a strong incoming flow can erode as a knickpoint even though it has
  nowhere further to send water itself. Erosion is gated on
  `max(local_slope, inflow_slope)`, and its driving "runoff" quantity is
  correspondingly `max(outflow, inflow)` for the same cell.
- **Deep drainage.** A closed basin has no natural outflow; without an
  explicit `DEEP_DRAINAGE_RATE` term removing water from `soil_moisture`
  every tick, sustained rain eventually saturates literally every cell
  given enough ticks, not just real convergence zones. This term is what
  keeps saturation localized to where terrain and vegetation actually make
  it likely.
- **Rain deposition uses `RAINFALL_DT_HOURS` (0.12), not "1 tick = 1
  hour".** A scripted `rainfall_mm_per_hour` rate is deposited as
  `rate * RAINFALL_DT_HOURS` per tick, so the displayed rate stays
  physically labeled (mm/hr) while ticks stay fine-grained.
- **Cohesion is a relaxing target, not a direct function of state.**
  `soil_cohesion` moves a fraction (`COHESION_RELAX_RATE`) of the way
  toward a target each tick, where the target is a documented linear
  combination of root density, organic content, and a saturation penalty
  (`erosion.py:_cohesion_target`). This lag is what makes "prior herbivore
  clearing" show up as a genuinely *earlier* cause of a *later* cohesion
  collapse, rather than an instantaneous side effect of the current tick's
  rain.
- **Root density lags biomass exponentially** (`ROOT_APPROACH_RATE`), for
  the same reason: grazing removes biomass immediately, but the root-system
  consequence -- and the vulnerability it creates -- shows up ticks later.
  This lag is what lets the acceptance scenario's "prior herbivore
  clearing" line be literally true rather than a narrative convenience.
- **A single cell can carry more than one feature over time.** A hollow can
  register as a `WaterPool` first and, as the same inflow undercuts it
  later, also become an `ErosiveGully`. `FeatureRegistry` guards duplicate
  creation per `(cell, feature_type)`, not per cell.

None of the thresholds or rates above are measured constants; they are
documented, tuned choices, all defined in `engine/config.py` with a comment
on what each one is for. Changing them changes the story the basin tells,
not just its cosmetics -- that's the point of keeping them in one file.

## Determinism and replay

"Deterministic replay from a known seed" is implemented as **re-execution**,
not as diff-application: a fresh `Simulation(seed, rain_schedule, ...)` run
for N ticks reproduces byte-identical final state and an identical event
log to any other run constructed the same way, within one implementation
(`tests/test_determinism.py`, `tests/test_replay.py` for the Python engine;
a one-off Node script for `engine.js` -- see README's Known Limitations).
A `RainSchedule` is intentionally stateless on both sides so the same
instance can safely be reused across multiple `Simulation` objects or
runs -- an early version of the Python engine had schedule state leak
between two simulations sharing one `RainSchedule`, which is exactly the
kind of hidden-state bug the "Determinism" tests exist to catch.

The live page ticks a real `Simulation` forward in the browser rather than
replaying a precomputed sequence -- an earlier version of this prototype
did the latter (a `run_demo.py`-generated snapshot sequence, scrubbed by
the viewer), which was scope-appropriate for a first pass but meant the
"simulation" on the public page wasn't actually running. `engine.js` is
the fix: a hand-ported mirror of the Python engine that runs live,
client-side, with no server and no precomputed data. See README's "Two
implementations, one design" for what that trade-off costs (no shared test
coverage, no cross-language determinism).

## Provenance model

Every significant, *edge-triggered* state transition -- a threshold being
crossed, not merely a value existing -- becomes an `Event` with an explicit
`caused_by` list of prior event ids (see `engine/events.py`,
`engine/simulation.py`'s `_record_*`/`_detect_*` methods). `Simulation`
tracks small per-cell pointers (`_last_saturation_event`,
`_last_root_loss_event`, `_last_cohesion_event`, plus one global
`_last_rain_event_id`) purely to wire `caused_by` correctly when a
downstream event fires; these pointers are bookkeeping, not part of the
causal record itself. `EventLog.lineage()` walks `caused_by` recursively to
produce the ordered ancestor chain a diagnostic card displays, and
`EventLog.is_acyclic()` verifies the resulting graph never loops.

`engine/lineage.py` (and its JS mirror in `web/toys/living-basin/app.js`) turns an event
chain into human-readable lines via a fixed per-`event_type` template that
only interpolates values already present on the event -- no free text
generation, no LLM, nothing that isn't already a stored number or string.

## Why the Diagnostic Card Can Be Trusted

Every field shown in a diagnostic card traces to stored data, not to a
recomputation from current world state:

- **Feature type / cells / genesis tick / status** -- copied verbatim from
  the `Feature` record (`features.json` on the Python side, the live
  `FeatureRegistry` in-memory on the JS side), set once at
  `FeatureRegistry.create`/`.create()` and never regenerated.
- **Causal lineage lines** -- each line is `EventLog.lineage()` output
  passed through `lineage.py`'s fixed template for that event's
  `event_type`; the numbers in the sentence (e.g. "Root density fell to
  0.14") are read directly from that specific `Event.inputs`, not from the
  feature or from the simulation's current state.
- **"Authored overrides: None"** -- only shown when neither the feature
  itself nor any event in its lineage has `authored_override = true`
  (`tests/test_provenance.py::test_no_override_reads_as_none` and
  `::test_authored_overrides_propagate_to_feature_status` check both
  directions).
- **Every cause referenced exists** -- `tests/test_provenance.py::
  test_all_displayed_causes_reference_existing_events` asserts every id in
  every event's `caused_by` resolves to a real stored `Event`; there is no
  code path that fabricates a `caused_by` entry.

The live page's JS lineage builder (`web/toys/living-basin/app.js`'s
`lineText`/`diagnosticCard`) is a line-for-line port of `engine/lineage.py`'s
templates, reading the same live `EventLog` `engine.js`'s `Simulation` is
writing to as it ticks -- it does not talk to a server or re-derive
anything from the rendered canvas.
