# The Living Basin -- v0 prototype

A small, inspectable causal simulation: a 64x64 terrain basin where
elevation, water, vegetation, herbivores, and erosion interact, and every
visible feature can explain its own causal history on click.

> **The central claim this prototype tries to earn:** every visible
> feature is an earned consequence of simulation state, and every
> displayed explanation is derived from recorded causes rather than
> generated afterward as decorative narrative. No feature is placed by
> hand, and no lineage text is written by an LLM -- see
> [*Why the Diagnostic Card Can Be Trusted*](#why-the-diagnostic-card-can-be-trusted).

This is a local prototype, not a deployed product: it's isolated under
`tools/living-basin/` with its own self-contained data pipeline, separate
from this repository's public `web/` site.

## How to run the simulation

No dependencies beyond Python 3's standard library.

```bash
cd tools/living-basin
python3 run_demo.py
```

This runs the one deterministic acceptance scenario (seed 42, ~300 ticks)
and writes `data/world_init.json`, `data/snapshots.json`,
`data/events.jsonl`, `data/features.json`, and `data/checksum.txt`.
`data/` is gitignored -- it's fully reproducible from `scenario.py` +
`engine/`, so it isn't checked in.

## How to open the interface

`data/` must exist (run the above first), and the viewer must be served
over HTTP, not opened as a `file://` URL (browsers block `fetch()` of local
files under `file://`):

```bash
cd tools/living-basin
python3 -m http.server 8000
# then open http://localhost:8000/viewer/ in a browser
```

This is a throwaway local dev server for your own machine -- stop it
(Ctrl-C) when you're done. It has no relationship to this repository's
production site.

## How to select the demonstration seed

The seed, rain schedule, herbivore start band, and tick count are all in
one place: `scenario.py`. There is currently one demonstration scenario
(`DEMO_SEED = 42`); to try another, edit those constants and re-run
`run_demo.py`. Nothing about seed selection is exposed in the viewer itself
in v0 -- see Known Limitations.

## How the simulation tick is ordered

Thirteen steps, fixed and documented in `engine/simulation.py`'s module
docstring and in [`ARCHITECTURE.md`](ARCHITECTURE.md#tick-pipeline-exact-order-see-simulationtick):
weather, rainfall, infiltration, flow redistribution, vegetation growth,
root-density update, herbivore movement + grazing, trail accumulation,
cohesion update, erosion, feature detection, provenance recording.

## How causal lineage is stored

Every significant *edge-triggered* state transition (a threshold being
crossed, not a value merely existing) becomes an append-only `Event` with
an explicit `caused_by` list of prior event ids
(`engine/events.py`). A feature's diagnostic card is built by recursively
walking that `caused_by` graph (`EventLog.lineage`) and rendering each
event through a fixed per-type text template (`engine/lineage.py`) --
never by inspecting current world state and never by an LLM. See
[`ARCHITECTURE.md`](ARCHITECTURE.md#provenance-model) for the full model.

## How authored overrides are detected

`engine/overrides.py:apply_override` is the only way to directly edit
simulation state outside the normal pipeline. It always records an
`override_applied` event (`authored_override=true`) and marks any feature
at that cell accordingly. A diagnostic card only says "No authored
overrides detected" when neither the feature nor anything in its lineage
carries that flag -- checked by
`tests/test_provenance.py::test_no_override_reads_as_none` and
`::test_authored_overrides_propagate_to_feature_status`. **v0 exposes no
editing UI** -- the data model and mechanism exist and are tested, but
nothing in the shipped scenario uses them, so every feature in the demo
run legitimately reads "None."

## Which aspects are intentionally simplified

- Hydrology is a documented, deliberately simple 8-neighbor steepest-descent
  flow model, not a physically accurate fluid simulation (see
  `hydrology.py`'s docstring and `ARCHITECTURE.md`).
- Weather is scripted rain events, not a weather model.
- Herbivores use weighted rules-based movement (biomass attraction, slope
  aversion, seeded randomness), not path planning or memory.
- "Deterministic replay" means re-executing the same seeded pipeline
  reproduces identical results -- not reconstructing state by applying a
  stored diff log to a starting snapshot. See `ARCHITECTURE.md`'s
  Determinism section for why, and for the one shared-mutable-state bug
  this design already caught.
- The viewer replays a **precomputed** snapshot sequence (every 5th tick by
  default) rather than driving a live, steppable backend -- there is no
  server in v0, only static files. This is explicit scope discipline (see
  the build packet's Non-Goals: "avoid architectural grandeur that delays
  the first inspectable causal loop"), not an oversight.

## Why the Diagnostic Card Can Be Trusted

- **Feature type / cells / genesis tick / status**: copied verbatim from
  the `Feature` record, fixed at creation.
- **Every causal-lineage line**: rendered from one specific stored `Event`'s
  `inputs` by a fixed template (`engine/lineage.py`, mirrored in
  `viewer/app.js`) -- the numbers you see are the numbers that were
  recorded at that tick, not a recomputation from the simulation's current
  state.
- **"Authored overrides: None"**: only shown when no event anywhere in the
  feature's lineage has `authored_override = true`.
- **No dangling causes**: every `caused_by` id resolves to a real stored
  event -- `tests/test_provenance.py` checks this directly against the
  full acceptance-scenario run, along with acyclicity.

Full detail, with file/line-level pointers: [`ARCHITECTURE.md`](ARCHITECTURE.md#why-the-diagnostic-card-can-be-trusted).

## Tests

```bash
cd tools/living-basin
python3 -m unittest discover -s tests
# or, if pytest is installed: pytest tests/
```

26 tests covering determinism, hydrology, vegetation/grazing, trails,
erosion (including "a gully cannot form without all four threshold
conditions" and "no rain -> no gully, ever"), provenance, and replay. No
external dependencies are required to run them (`unittest` is stdlib);
they're also pytest-discoverable since `pytest` understands
`unittest.TestCase`. The suite takes roughly 100 seconds -- most of that
is pure-Python 64x64-grid tick computation in the handful of tests that run
a full or near-full simulation, not I/O.

## Known limitations

- **No live parameter tweaking or steppable server.** Playback scrubs
  through a precomputed run; changing the scenario means editing
  `scenario.py` and re-running `run_demo.py`.
- **The sample screenshot in this README is not a live browser capture.**
  No headless browser was available in the environment this was built in
  to screenshot the actual canvas, so `docs/sample-screenshot.png` was
  generated by a separate offscreen script reading the same `data/`
  files the real viewer reads. The JS lineage/rendering logic itself was
  verified against the real data with Node (see commit history / dev
  notes), and the HTTP-served data paths were checked with `curl` -- but
  actually opening `viewer/index.html` in a real browser and clicking
  around has not been done by the author of this prototype. Please do
  that verification pass before treating the interface itself as proven.
- **Thresholds and rates are provisional**, documented in
  `engine/config.py`, and were tuned empirically against this one seed to
  produce a full causal chain (trail -> grazing -> root loss -> rain ->
  saturation -> erosion -> gully) within a reasonable tick budget -- not
  derived from any physical measurement. Changing the seed or scenario may
  require re-tuning them.
- **No biological realism, ecosystem, animal cognition, climate model,
  large-scale geology, multiplayer, or general simulation platform** --
  all explicitly out of scope for v0, per the build packet's Non-Goals.
- **Single-cell features only.** `WaterPool`/`HerbivoreTrail`/`GrazedPatch`/
  `ErosiveGully` currently each register as a single cell, not a merged
  multi-cell region, even when adjacent cells cross the same threshold
  independently. Good enough to prove the causal-provenance loop; a real
  region-growing pass is future work.
